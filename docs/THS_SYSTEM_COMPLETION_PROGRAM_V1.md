## How to make a checkmark real

1. **Select the existing owning workstream, ticket and exact expected outcome.** Check `CURRENT_SPRINT` and GitHub. Do not self-admit an item simply because it appears here. Underlying source-specific checklist remains canonical.
2. **Break down current acceptance into observable subproofs** (e.g., exact source and content hash; negative tests; required CI/build; review decision; protected merge; live deployment; actual field outcome). Some gates require independent human or calibrated craft/science proof. Not all subproofs have equal weight or apply to every task.
3. **Record for each gate:** `ID`, `owner ticket/PR`, `scope`, `date`, `exact-head/source SHA`, `observed acceptance evidence URLs`, `unmet acceptance bullets`, `state`, `next smallest action`, `blocker` and `outcome impact` (if measured). Proposed states: `NOT_AUDITED`, `IN_PROGRESS`, `BLOCKED`, `FAILED`, `ACCEPTED`; all unmeasured external values `Unknown`.
4. **Calculate only evidence-based progress**: `accepted gates / audited or defined gates` and separate `current gate verified subproofs / required subproofs` *after* scopes and denominators are explicitly fixed. Example: 3 verified subproofs out of 5 means `3/5 (60%)` **for that gate only**, not `60% of system complete`. Do not invent +1% progress just to avoid repeating a number; give concrete delta in verified work if the fraction legitimately does not change.
5. **Recompute and downgrade when assumptions change.** Changed sources, voice bytes, deployment, permissions, field data, rights, or quality evidence can invalidate a prior check. Code merged does not prove deployed, approved for publication, used by an audience, legally transferable, or profitable.

## What happens next

- Start with an **evidence-only audit** of existing source/PR/CI and presently available production/outcome receipts, mapping them to the 128 questions. A code-present result is not an `ACCEPTED` full outcome.
- For high-priority gaps, use the *existing* backlog scoring formula: `(Business Impact × User Value × Traffic Potential × Strategic Leverage × Confidence) / Effort`, subject to hard safety/science/security gates; no second prioritization model.
- Prefer a sequence with measurable real-world wins: **EvidenceMotion excellent video**, **source-safe evidence/article**, **publisher/observer verified post**, **consented GA4/GSC/affiliate measurement**, **reproducible efficiency**, then **verified commercial lift/independent licensing demand**. These are milestones, not a forced reranking of admitted work.
- Updates should include `SUCCESS/PARTIAL/FAIL/BLOCKED`, before→after facts, exact proof, accepted gate change (if any), present partial-step measured fraction where available, and unresolved blocker. Never claim a scheduler, CI, deployment or business result without verifying it.
- Adding new systems means first proving a genuinely new non-overlapping owner and value mechanism; otherwise extend the closest existing checklist. No fourth normal D/R/A lane, no new scheduler, no automatic posting, no unapproved medical claims, no paid dependencies, and no license change from this document.

**Owner-facing summary:** Think of the 16 rows as the *instrument panel*, not 16 simultaneous projects. A system only earns DONE when it reliably produces the end-user/business result it was created for.
