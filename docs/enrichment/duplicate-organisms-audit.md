# Duplicate-organism audit

Two entities carrying the same `latin_name` describe the same organism. Sometimes
that is deliberate — a plant part or preparation with its own evidence base — and
sometimes it is a duplicate that grew from a slug and a common name being added
at different times.

**Resolved 2026-08-24.** 34 `latin_name` values are shared. After consolidation
**5 still serve two or more live profiles, and all five are deliberate splits.**
12 are resolved by a 301.

```bash
npm run enrich:duplicates            # current state
npm run enrich:duplicates -- --plan  # proposals, if any remain
npm run enrich:duplicates -- --json  # machine-readable
```

The problem was surfaced by the shared-value guard added in batch 3, then
confirmed by sweeping values that were already populated before any enrichment
ran. `audit:duplicates` did not catch it: it checks duplicate *slugs*, and every
one of these pairs has distinct slugs.

---

## 1. How liveness is measured

Not from `runtime_export_decision`. A redirected entity keeps
`full_public_runtime` in the workbook while the build emits no page for it, so
the column overstates. Liveness comes from
`public/data/runtime-manifests/route-manifest.json` — generated by the build and
committed, so available without one — intersected with `public/_redirects`.
Against `out/sitemap.xml` the two agree on 11 of 12 contested entities.

`source_count` is not a usable signal either. **It is a stale counter that tracks
nothing**: `glycyrrhiza-glabra` claims 24 while rendering the same three
citations as `licorice`, which claims 7. Ranking survivors by it produced eight
false "the side being retired is richer" warnings, all of which dissolved when
measured against the built pages.

> Two earlier counts in this document were wrong. The first (22 live duplicates)
> read the workbook column. A follow-on claim that redirected pages were still
> indexed came from reading `indexable-herbs.json` as if it were the sitemap; it
> is not, and `validate:redirect-indexability` (THS-177) already covers that case
> and reports clean.

## 2. The five that remain — all legitimate

Filtered automatically: one side is a part, a preparation, or the compound rather
than the source organism.

| value | entities | why |
|-------|----------|-----|
| *Camellia sinensis* | `black-tea`, `camellia-sinensis`, `green-tea-extract` | one plant, three preparations |
| *Schisandra chinensis* | `schisandra`, `schisandra-berry`, `schisandra-chinensis` | `schisandra-berry` is the fruit |
| *Morus alba* | `morus-alba`, `mulberry-leaf` | `mulberry-leaf` is the leaf |
| *Nigella sativa* | `nigella-sativa`, `black-seed` | `black-seed` is the seed |
| *Curcuma longa* | `curcumin`, `turmeric` | curcumin is the compound, turmeric the plant |

`curcumin` is typed `entity_type: herb`, so the type check cannot see it; it is
listed explicitly in `KNOWN_NON_DUPLICATES`.

## 3. What was consolidated

Thirteen merges. Each retired entity took the same six-column shape the
already-retired aliases (`bcaas`, `nr`) use — `alias_redirect_only`, `noindex`,
`redirect_only`, `alias_redirect`, `minimal`, `redirect_resolution_only` —
applied through `scripts/data/edit-entity-master-cell.mjs`, since those columns
are protected from the enrichment patch pipeline by design.

### The ranking rule

Content decides when the gap is material: an unbuilt page, or two or more extra
rendered citations. Otherwise content is at parity and the site's own precedent
applies, keeping the **common-name** slug — which is what all nine pre-existing
herb redirects do (`allium-sativum`→`garlic`,
`withania-somnifera`→`ashwagandha`, `silybum-marianum`→`milk-thistle`, …).

Twelve of thirteen pairs were at parity: three rendered citations each, within
about 10% on page size. Ranking on real content rather than the stale column
flipped two proposals, both of which precedent alone would have got backwards.

Implemented in `proposeResolution` in
`scripts/enrichment-pipeline/lib/duplicate-organisms.mjs`.

## 4. What the pipeline will and will not do

`entity_type`, `slug`, `runtime_export_decision`, `seo_indexing_recommendation`,
and every other publishing control are **prohibited** to the enrichment pipeline
by contract. It cannot merge entities, redirect slugs, or unpublish a profile.
The consolidation above was applied by an operator script driving the surgical
editor, not by the pipeline.

What the pipeline does is refuse to make the problem worse: a `latin_name` that
another entity already holds routes to review instead of importing, unless the
change carries an explicit `shared_value_acknowledged` reason.

## 5. Applying a further merge

1. Move any sources or evidence worth keeping onto the survivor.
2. Add both redirect lines to `public/_redirects` — source with and without a
   trailing slash, target always with one — then run `npm run redirects:normalize`
   to flatten chains and re-point any absolute `www.` rule at the new target.
3. Set the retired entity to the six-column retired shape via
   `npm run workbook:edit -- --slug <slug> --column <column> --value <value>`.
4. `npm run enrich:duplicates` — the live count should fall.
