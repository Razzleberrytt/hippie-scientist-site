# Canonical Data Ownership — 2026-08-21

Which source owns which field, and which "generated" outputs are in fact
source data. Written because several defects in this repair traced back to the
same root: a value was enriched in generated output and then regenerated away,
or existed in two places that disagreed.

## The rule that does not hold

`CLAUDE.md` states that all runtime JSON in `public/data/**` is generated and
disposable, regenerated by `npm run data:build`. **That is not true of the
detail payloads.**

`scripts/data/build-runtime-from-workbook.mjs` does not write
`herbs-detail/` or `compounds-detail/` at all. Running it into an empty
directory produces `herbs.json`, `compounds.json`, indexes and maps — and no
detail files. The only scripts that write them are
`scripts/build-runtime-data.mjs` and `scripts/generate-monograph-projection.mjs`,
**neither of which is called by any npm script, pipeline or workflow.**

So `public/data/{herbs,compounds}-detail/*.json` are de facto **source data**:
committed, never regenerated from scratch, and mutated in place by later
pipeline steps. Treating them as disposable is what made enrichment losable.

## Ownership table

| Field | Owner | Regenerated by | Notes |

| Detail payloads (`*-detail/*.json`) | **The files themselves** | Nothing | De facto source. Mutated in place by postprocess, participant counts, governance overlay, canonical citation export. |
| Citation identifiers (PMID / DOI / URL) | Workbook | Canonical citation export | |
| **Citation titles** | `ops/cache/pubmed-metadata.json` | `apply-pubmed-metadata.ts` | Committed NCBI cache, 849 records. The workbook holds placeholders for 157 of them. |
| Study design / journal / year / authors | `ops/cache/pubmed-metadata.json` | `apply-pubmed-metadata.ts` | Filled only where empty; curated values win. |
| Evidence levels & grades | Workbook | `normalize-evidence-grades.ts` | |

| Indexability (authoritative) | Governance overlay | `build-runtime-summary-indexes.mjs` → `summary-indexes/` | What `app/sitemap.ts` and page metadata read. |

## The enrichment loss, explained

`fetch-pubmed-metadata.mjs` retrieves real bibliographic titles from NCBI and
caches them in `ops/cache/pubmed-metadata.json` (committed).
`apply-pubmed-metadata.ts` writes them into the detail payloads. But the apply
step was in no pipeline, and two pipeline steps overwrite titles from the
workbook — the payload postprocess and the canonical citation export inside
`build-runtime-summary-indexes.mjs`.

Every `data:build` therefore replaced **182 real study titles** with the
workbook's placeholder, 157 of them reading "PubMed PMID *n*. Minimal citation
row added from existing workbook PMID…", while leaving `metadataSource:
'pubmed'` on the record — a provenance flag asserting PubMed supplied a value
that is in fact a note about PubMed *not* having supplied it.

**Fixed** by running the apply step inside `data:build`, `check:data` and the
deploy, positioned *after* the canonical citation export that used to revert it,
and again before the derived artifacts are built so those see real titles.
Proven by `lib/__tests__/citation-enrichment-durability.test.ts` and by building
twice: 1,800 files, 0 semantic differences.

## Two more surfaces that ship without being regenerated

**The production deploy skips most of `data:build`.**
`scripts/build-deploy.mjs` parses the workbook and then jumps to
`build-related-runtime-maps`. It never ran `postprocess-workbook-payloads`,
`apply-participant-counts`, `apply-governance-overlay`, the PubMed apply, or any
sanitizer. Production therefore ships the committed payloads. This is why the
editorial leak was live rather than theoretical, and why detail-file governance
verdicts are frozen. Enrichment, sanitization and the leak gate are now steps in
the deploy; the governance overlay deliberately is not, because adding it moves
roughly 129 profiles' indexing and deserves its own review.

**The root summary files are orphaned duplicates.** Nothing regenerates
`public/data/herbs-summary.json` or `compounds-summary.json`, yet the search
experience and the on-demand comparison tool fetch them at runtime. They carried
36 editorial instructions until this repair, and they still carry a legacy shape
that shares only 4 keys with `summary-indexes/`. **A human should decide whether
to retire them or wire their generator into the pipeline** — until then they are
sanitized in place by `sanitize-public-text.mjs`, which runs over the whole
corpus rather than over a list of known files precisely so orphans are covered.

## Runtime maps with dead inputs

| File | Keys | Relationships | Consumed? | Verdict |
|---|---|---|---|---|
| `runtime-maps/ecosystem-map.json` | 838 | **0** | Yes — `lib/ecosystem-continuity.ts` via `getRuntimeMapEntries('ecosystem', …)` | **Broken, not dead** |
| `runtime-maps/authority-hubs.json` | 0 | 0 | No — `getAuthorityHubsMap` is never called | **Dead** |

`buildEcosystemMap` keys off `collectEcosystemSignals`, which reads
`topic_clusters`, `ecosystem_tags`, `pathway_companions`, `ecosystem_anchors`,
`pathway_ecosystems`, `mechanism_ecosystems` and others. **Every one of those
fields is absent from all 856 records.** `buildAuthorityHubs` reads
`authority_supernode` / `authority_status` / `evidence_authority_status` — also
absent from all 856.

So the ecosystem-continuity feature runs against a map that is structurally
present and permanently empty: 838 slugs each mapped to `[]`.

**Not repaired, deliberately.** The inputs do not exist anywhere in the corpus,
so relationships cannot be derived from legitimate existing data — only
invented. Per the brief, empty files are not to be populated with fabricated
semantic relationships. This needs a human to decide whether to restore the
workbook columns that fed these signals or retire the feature.

## Stacking vs comparison

`build-related-runtime-maps.mjs` derives `comparison-map.json` and
`stack-map.json` from the same signal-overlap scoring used for related profiles.
A shared mechanism makes two substances *similar*, which is an argument for
presenting them as **alternatives** and, on its own, an argument *against*
stacking them — two serotonergic compounds overlap precisely where combining
them carries risk.

Nothing in this repair changed those maps. The flaw is recorded here because
"similar" and "safe to combine" are different claims and the generator does not
distinguish them. **A human should decide** whether automated stacking
suggestions are derivable at all from current data, or should be reduced to
evidence-backed pairs only.

## Recommended follow-ups

1. Correct `CLAUDE.md`: detail payloads are not disposable.
2. Decide the fate of the orphaned root summary files.
3. Decide whether to restore ecosystem signal columns or retire ecosystem continuity.
4. Decide whether stacking recommendations should be derived from similarity at all.
5. Decide whether the deploy should run the governance overlay.
